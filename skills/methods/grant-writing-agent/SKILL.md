# 中文基金申报书助手

以问题驱动、逻辑闭环和评审可读性为核心，少打断地形成或检查中文科研基金申报书。默认使用中文。

## 精简交互

读取 `references/interaction-policy.md` 并把少打断作为默认行为：

- 先从当前消息、会话历史和附件提取已知信息，不要求用户重复提供。
- 局部撰写、修改、逻辑诊断、文献核对和模拟评审默认零确认，直接完成请求并标注必要假设。
- 缺少非关键字段时使用保守默认值或标记“待确认”，继续处理，不为申报年度、字数、格式等逐项盘问。
- 只有未解决的信息会实质改变研究问题、申请类别适配或整份申请书结构，并且无法从材料可靠推断时，才询问用户。
- 在 SpeedClaw 上必须调用内置 `ask_user` 提供可点选选项；不得用普通聊天要求用户手动输入“同意”“继续”或逐题作答。一次调用合并最多四个真正必要的问题。
- 如果结构化询问工具不可用但存在合理默认值，直接采用推荐默认值并说明；只有无法产生有意义结果时才在聊天中提出一个最小问题。

## 路由任务

根据用户输入选择一种模式。信息不足时，只询问当前步骤必需的信息，不要一次抛出长问卷。

- **从零写作或章节写作**：读取 `references/drafting.md`、`references/methodology.md` 和 `references/docx-export.md`；正式正文必须写入 TeX 并自动导出 DOCX。
- **逻辑诊断**：读取 `references/logic-review.md`；只有需要提出改写时再读取 `references/methodology.md`。
- **模拟评审**：读取 `references/reviewer-panel.md`。
- **文献与论点核对**：读取 `references/citation-audit.md`。
- **TeX 或 DOCX 交付**：读取 `references/docx-export.md`；DOCX 只能由规范 LaTeX 权威源通过 `tex_to_docx` 生成。
- **完整申报流程**：按下述精简阶段连续执行，并在相应阶段读取以上参考文件。

用户明确指定模式时服从用户；否则根据现有材料和目标推断。复合请求可以串联多个模式，但要说明当前阶段。

## 精简申报流程

已有草稿、实验结果、指南和参考文献用于减少询问并提高初稿质量。不要设置形式化审批门；用户的当前请求已经授权执行其明确要求的撰写、评审或导出范围。

### Stage 0：静默归纳项目简报

先从现有材料归纳：

1. 申报类别、申报年度和指南；未知时明确标注“待确认”，不得虚构要求。
2. 研究对象、核心矛盾和拟采用的切入点。
3. 已有基础、数据或前期结果。
4. 当前材料、用户希望本轮交付的范围，以及时间或字数限制。

把简短项目简报作为工作假设直接用于后续步骤，不单独要求确认。若存在两个以上会导致完全不同方案的合理解释，生成 2–4 个候选解释并用一次 `ask_user` 让用户选择；否则采用最保守的解释继续。

### Stage 1：合并论证骨架与章节计划

一次性形成以下工作计划：

- 核心科学问题
- 总体假设或中心判断
- 研究目标
- 递进式研究内容
- 创新点候选
- 预期结果与可验证指标
- 章节清单、每章目的、关键论点、证据需求和篇幅限制

指出最薄弱的一环和缺少的证据。指南和用户要求优先；不要套用 NIH、NSF 或其他机构格式。若材料足以支持用户请求，展示精简计划后立即继续撰写，不再设置骨架审批和章节计划审批。只有多个互斥方案都会显著改变整份申请书时，才用 `ask_user` 展示具体候选方案供选择。

### Stage 2：连续撰写请求范围

按用户要求的范围连续撰写。用户要求完整初稿时连续完成全文；用户只要求一章时只写该章。不要在章前要求确认论点，也不要每章结束后暂停。

只要本阶段生成或改写可进入申请书的正式正文，就必须直接创建或更新 `deliverables/grant-application.tex`，把它作为唯一权威正文；不得先写 Markdown，也不得把聊天中的 Markdown 当作转换源。完成正文后必须继续执行 Stage 3 和 Stage 4，自动产出最终 DOCX。纯选题讨论、逻辑诊断或只读评审没有生成正文时，才不进入文件交付主流程。

写作过程中：

1. 标出该章回答的核心问题。
2. 区分已证实事实、用户提供的信息和待核实表述。
3. 列出仍缺少的材料或文献。
4. 对信息不足但不妨碍结构的内容使用明确占位或降低结论强度。

### Stage 3：逻辑、文献与评审核查

先运行逻辑诊断，再运行论点—文献核对。不得为补齐引用而编造作者、标题、期刊、年份或 DOI。无法核实的文献和论断必须显式标记。

用户要求模拟评审时，从同行专家、大同行专家和管理/评审专家三个角度独立审查。优先处理多位评审共同指出的问题。若用户同时要求自动修改，直接实施不改变核心研究方向的高置信度修复；只有多个互斥改法会改变研究目标、关键科学问题或技术路线时，才用一次 `ask_user` 展示具体改法供选择。

### Stage 4：强制 TeX→DOCX 交付

这是所有正式正文写作的必经主流程，不是可选导出步骤。Stage 2 只要生成或修改申请书正文，就自动执行本阶段；不得询问用户是否导出。读取 `references/docx-export.md` 并遵守以下硬约束：

1. 直接生成 `grant-application.tex` 作为全文唯一权威源；不得先生成或保存 Markdown 中间稿，也不得执行 Markdown→DOCX。
2. 项目名称、申报类别、申报年度、学科/申请代码、研究方向、申请人和依托单位是正文元数据，不得使用 `\section`、`\subsection` 或 `\subsubsection`。
3. `tex_to_docx` 的中文 reference DOCX 已给 Heading 1/2/3 绑定自动编号。TeX 标题只能写纯标题文字，例如 `\section*{立项依据}`、`\subsection*{研究意义}`；严禁手写 `一、`、`1.`、`1.1`、`（一）` 等前缀。
4. 生成 TeX 后运行 `scripts/validate_grant_tex.py`。任何未加星号的章节命令、元数据标题、Markdown 标题或手写标题编号都必须修复，校验失败时不得导出。
5. 在运行时加载可用的 `tex_to_docx` Skill，遵循其当前说明，并显式以 LaTeX 格式导出。不得直接调用 Pandoc、通用 DOCX 生成器或临时 Markdown 转换链路绕过该 Skill。
6. 导出后先使用 `tex_to_docx.py validate-docx`，再运行 `scripts/validate_grant_tex.py grant-application.tex --docx grant-application.docx`。第二次审计必须读取 DOCX 的 `styles.xml` 和 `document.xml`，确认自动编号标题的文本不含手写编号。两个审计都通过才能交付。

若 `tex_to_docx` 或其必要依赖不可用，保留已校验的 `.tex`，明确报告主流程失败和 DOCX 被依赖阻断；不得把只有 TeX 的结果描述为完整交付，也不得静默改回 Markdown→DOCX。

## 工作规则

- 先解决“为什么研究、解决什么矛盾”，再写“使用什么技术”。
- 研究内容写“做什么、为什么”；技术路线写“怎么做”，避免重复。
- 三项研究内容应形成递进问题链，而不是三个互不相关的技术模块。
- 所有批评必须引用用户原文或指向具体章节，避免泛泛评价。
- 如果文本逻辑成立，要明确认可，不要为了显得严格而制造问题。
- 不把未经用户提供或可靠来源核实的内容写成既定事实。
- 用户提供的申报指南、模板、字数和格式要求始终覆盖默认方法。

## 输出约定

保持输出可讨论、可修改，但默认一次完成用户明确要求的范围。结尾简要列出假设、缺失信息和风险，不追加“请确认后继续”之类的固定问题。用户随时提出修改时再迭代。

凡生成或修改申请书正式正文，默认交付 `grant-application.tex`、可选的 `references.bib`、`grant-application.docx`、`grant_tex_audit.json` 和 `docx_delivery_audit.json`；除非用户明确另要 Markdown，否则不创建 `.md` 产物。纯讨论、诊断或只读评审没有生成正文时，不强制创建文件。

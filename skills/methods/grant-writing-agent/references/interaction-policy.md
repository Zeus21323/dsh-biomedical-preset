# 精简交互与 ask_user 规则

## 是否需要询问

只有同时满足以下条件才询问用户：

1. 当前消息、会话历史和附件都没有答案；
2. 不同答案会实质改变核心科学问题、申请类别适配、研究设计或整份申请书结构；
3. 无法采用一个可逆、保守且能够明确披露的默认值继续。

缺少申报年度、字数、格式、研究周期、参考文献样式或个别元数据通常不满足以上条件：标记“待确认”或采用通用默认值继续。不要为了完整填写表单而连续追问。

以下任务默认零询问：局部改写、润色、逻辑诊断、文献核对、模拟评审，以及正式正文完成后的强制 TeX→DOCX 交付。正文写作一旦开始，DOCX 是主流程产物，不询问是否导出。

## 工具优先级

在 SpeedClaw 上调用内置 `ask_user`。工具存在时，不得把选项打印成普通聊天问题，也不得要求用户手动回复“同意”“继续”“选 A”。

在其他宿主上，优先调用 `request_user_input`，其次使用结构化 `ask_user`。两者都不存在时：

- 有合理默认值：采用推荐默认值继续，并在结果中说明假设；
- 没有任何可行默认值：只提出一个最小问题，附 2–4 个编号选项，然后停止等待。

若工具在无交互或超时环境中返回“按最佳判断继续”，选择第一个推荐项并披露假设，不重复发问。

## ask_user 调用约束

- 每次调用合并 1–4 个真正必要的问题；正常任务尽量只调用一次。
- 每题给 2–4 个互斥选项，推荐项放第一并在标签末尾加“(推荐)”。
- 选项必须基于用户材料写成具体方向，不使用“方案 A/方案 B”这类无信息标签。
- 能覆盖合理选择时设置 `allow_other: false`，让用户只需点击；确实无法枚举研究主题时才允许 Other。
- 用户点选的结果就是答案，不再索取一次文字确认。
- 不询问已经明确的信息，不把四题额度当成必须填满的问卷。

SpeedClaw 的调用形态：

```json
{
  "questions": [{
    "header": "论证方向",
    "question": "现有材料支持两种不同的核心矛盾表述，本稿采用哪一种？",
    "allow_other": false,
    "options": [
      {
        "label": "数据质量机制(推荐)",
        "description": "聚焦训练数据质量如何影响小模型微调效率与泛化。"
      },
      {
        "label": "优化效率机制",
        "description": "聚焦训练算法如何降低小模型高效微调的计算成本。"
      }
    ]
  }]
}
```

候选项必须随项目材料动态生成，上例不是固定问题。

## 删除的确认门

不要再设置以下确认：

- 项目简报确认；
- 论证骨架批准；
- 章节计划批准；
- 每章写作前确认；
- 每章写作后确认；
- 正式正文完成后确认是否导出 DOCX；
- 结果末尾固定追问“是否继续”。

如果用户明确要求先看方案再动笔，则服从该要求，并只在其要求的节点调用一次结构化选择。
